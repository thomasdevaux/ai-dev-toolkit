# Reference — Wails Project Architecture (Go + React)

Selection grid, target folder structures, and audit checklist. Parallel in structure to the Tauri reference — same principles, adapted to Go and Wails' toolchain.
Forge-neutral. No CI considerations.

## 1. The decisions that actually matter

| # | Decision | Options | Impact |
|---|---|---|---|
| W1 | Where does business logic live? | React / split / Go | Determines the profile |
| W2 | Shape of the Go↔JS boundary | thin bound methods / use-case-oriented / broad convenience binding | Very expensive to change later, and doubles as the de facto security boundary (no capability system exists) |
| W3 | Go-side state | struct fields / `sync.Mutex` / `sync.RWMutex` / channels (actor-shaped) | Testability and race conditions |
| W4 | Error boundary | bare `error` (serializes to a JS exception string) / typed result struct | Whether the frontend can react precisely |
| W5 | Long-running / progress | blocking bound calls / `EventsEmit`/`EventsOn` | UX on heavy tasks |
| W6 | Frontend location | `frontend/` (Wails default) | No configuration cost either way — this is already the tool's default, unlike Tauri |

**W2 is the structuring decision**, same role D2 plays in the Tauri skill — and it carries extra weight here because it's also the only thing standing in for a permissions model.

---

## 2. Choosing a profile

| Criterion | A. The Storefront | B. The Workshop | C. The Engine |
|---|---|---|---|
| Business logic | React | React (workflow) + Go (system) | Go |
| System access | Low or none | Frequent | Central |
| Reuse outside desktop | No | Rare | Explicit goal, including a server exposing the logic to remote clients |
| Team size | 1–3, front only | Small mixed team | Dedicated Go skills |
| Maturity | Prototype / MVP | Growing product | Platform / engine |
| Tooling complexity | Low | Moderate | Moderate (Go's tooling is lighter than Cargo workspaces) |

### Decision rules

- **Default: B (The Workshop).**
- **A** only if the app is an interface over a remote API with no significant system access.
- **C** only with a real, identified second consumer.

## 3. Profiles and folder structures

### A. The Storefront

Go limited to bootstrapping and window setup.

```text
my-app/
├── frontend/                     # React app (Wails default location)
│   ├── src/
│   │   ├── components/
│   │   ├── pages/
│   │   ├── api/                  # remote HTTP calls, not Wails bindings
│   │   ├── App.tsx
│   │   └── main.tsx
│   ├── package.json
│   └── vite.config.ts
│
├── app.go                        # bound struct, thin
├── main.go                       # wails.Run(...), asset embedding, bootstrap only
├── wails.json
├── go.mod
├── build/
│   └── appicon.png
└── README.md
```

**Target**: MVP, dashboard, REST client, simple tool.

---

### B. The Workshop (recommended default)

```text
my-app/
├── frontend/                     # React app (Wails default location)
│   ├── src/
│   │   ├── components/           # pure presentation, no bindings calls
│   │   ├── features/
│   │   │   └── <feature>/
│   │   │       ├── components/
│   │   │       ├── hooks/
│   │   │       └── index.ts
│   │   ├── pages/
│   │   ├── ipc/                  # THE ONLY place generated bindings are called
│   │   │   ├── client.ts         # wraps generated calls, maps typed errors
│   │   │   └── <domain>.ts
│   │   ├── bindings/             # generated by `wails generate module` — do not edit
│   │   ├── store/
│   │   ├── lib/
│   │   ├── App.tsx
│   │   └── main.tsx
│   ├── package.json
│   └── vite.config.ts
│
├── internal/                     # Go-enforced private packages, not importable outside the module
│   ├── domain/                   # business logic, no Wails/context imports, testable standalone
│   │   └── <domain>/
│   ├── infra/                    # adapters: fs, git, process, http
│   ├── state/                    # AppState struct + locking policy
│   └── apperror/                 # typed error result shared by every bound method
│
├── app.go                        # bound struct(s) — thin exposure, calls internal/domain
├── main.go                       # bootstrap only
├── wails.json
├── go.mod
├── build/
└── README.md
```

**Split of responsibilities**:

| React | Go |
|---|---|
| UI, navigation, forms, screen state | Files, Git, processes, low-level networking |
| User journey orchestration | Persistence, migrations |
| Display validation | Authoritative business validation |
| — | CPU-bound processing |

**`internal/` is doing real work here, not just convention**: Go's compiler enforces that `internal/` packages are only importable from within the same module tree — this is a language-level guarantee the Tauri/Rust skill doesn't have an exact equivalent for (Rust's `pub(crate)` is close but less commonly leveraged this way). Use it deliberately: nothing outside the app should import `internal/domain` directly.

**Target**: IDEs, developer tooling, document management, classic desktop apps.

---

### B — variant: CLI access without a second binary

When a CLI companion is wanted but the single-binary, dual-mode option was chosen (see the decision table in `SKILL.md`), this stays entirely inside profile B's shape — no multi-binary layout needed. Only `main.go` changes:

```go
// main.go
func main() {
    if len(os.Args) > 1 {
        cli.Run(os.Args[1:])   // CLI mode — never calls wails.Run
        return
    }
    // no args — launch the window as usual
    err := wails.Run(&options.App{ /* ... */ })
    if err != nil {
        log.Fatal(err)
    }
}
```

Both paths call the same `internal/domain` functions. The CLI path never calls `wails.Run`, so no window is created in that mode. The trade-off from the decision table still applies: the compiled binary includes Wails regardless of which path executes, and nothing but code review stops CLI code from accidentally reaching into `app.go`'s bound methods or GUI-only state.

### C. The Engine — variant: two separate binaries

Business logic in Go, organized so a second, genuinely separate binary (CLI, server) can use it without going through Wails at all. This is the heavier structure — only reach for it when the two-separate-binaries choice was made deliberately (see the decision table in `SKILL.md`), not merely because a CLI was wanted at all.

```text
my-app/
├── cmd/
│   ├── desktop/
│   │   ├── frontend/
│   │   │   └── src/               # UI, only calls bound methods
│   │   ├── app.go                 # thin exposure over internal/domain
│   │   ├── main.go
│   │   └── wails.json
│   └── cli/
│       └── main.go                # 2nd binary — has no Wails dependency at all
│
├── internal/
│   ├── core/                      # types, errors, config
│   ├── domain/                    # pure business rules
│   └── <capability>/              # git, filesystem... on evidence
│
├── go.mod                          # single module — keeps internal/ visibility simple
└── README.md
```

**`cmd/`**: the standard Go convention for a module producing multiple binaries (`golang-standards/project-layout`), unlike the equivalent Rust and Python skills which use `apps/` following the JS-monorepo convention their hybrid Tauri/web tooling already leans on. The names differ across this portfolio because each follows what's native to its own ecosystem, rather than forcing one name everywhere.

**Constraint on Go modules**: keep this as a **single Go module** (one `go.mod` at the root) with `cmd/desktop` and `cmd/cli` as separate `main` packages inside it. This keeps `internal/` visibility working without extra ceremony. Only split into multiple modules via a `go.work` workspace if independent versioning or release cadence between the apps is a real requirement — not by default.

**Second consumer is a server**: swap or add `cmd/server/` (a standard `net/http` or a router like `chi`/`echo`), consuming the same `internal/domain`. See §9.

**Target**: complex software, platforms, multi-frontend apps.

## 4. Cross-cutting decisions in detail

### W2 — Shape of the Go↔JS boundary
A bound method should: receive the call, invoke `internal/domain`, map any error into the typed result, return. If `app.go`'s methods mirror `internal/domain` function-for-function, the layer adds nothing.

Granularity: prefer **use-case-oriented** bound methods (`OpenProject`) over **technical CRUD** (`ReadFile`, `ParseConfig`, `ValidateConfig`). This matters even more in Wails than in Tauri, because every bound method is also a permission grant — there's no separate manifest to narrow later.

### W3 — Go-side state
- Prefer stateless where possible.
- Struct fields on the bound App type for simple shared state; guard with `sync.Mutex` or `sync.RWMutex` when accessed from multiple goroutines (Wails event handlers and bound methods can both run concurrently).
- For anything with multiple interdependent pieces of state, prefer a single goroutine owning the state and communicating via channels — Go's idiomatic actor shape — over multiple mutexes.

### W4 — Error boundary
A bare Go `error` returned from a bound method serializes to a JS exception carrying only the error's string message — the same structural problem as Tauri's "String error" anti-pattern, just reached by a different default. Define a shared result shape instead:

```go
type Result[T any] struct {
    Data T      `json:"data,omitempty"`
    Error *AppError `json:"error,omitempty"`
}

type AppError struct {
    Code    string `json:"code"`    // stable discriminant, e.g. "FILE_NOT_FOUND"
    Message string `json:"message"` // safe to display, no internal details
}
```

Log the internal detail server-side (Go's structured logging), keep `Message` safe for display, and let the frontend switch on `Code`.

### W5 — Long-running work
Wails' event system (`runtime.EventsEmit(ctx, "event-name", data)` in Go, `EventsOn("event-name", callback)` in JS) is broadcast-shaped by default — any listener gets any emitted event. For per-call progress where only the calling component should receive updates, include a request ID in the event name (e.g. `"progress:" + requestID`) or in the payload and filter client-side. There's no built-in per-call channel primitive equivalent to Tauri's Channel type — this pattern is the practical substitute.

### W6 — Frontend location
`wails init` already scaffolds `frontend/` as a subfolder with Go files at the root — this is the inverse of Tauri's default (frontend at root, Go in a subfolder). Don't fight this default; there's no configuration cost either way since it's what the tool already does.

### Security — no capability system
Restated because it's easy to underweight: everything bound is fully privileged. The practical mitigation is treating `Bind()` calls as the permission boundary — review them the way you'd review a Tauri capabilities file, even though no such file exists here.

### Testing
- Go: standard `_test.go` files co-located with `internal/domain`; that package must build and test without importing Wails' `context` runtime.
- Frontend: same as the shared React reference — vitest, `ipc/` mocked at its boundary.

## 5. Scaffolding rules

1. Determine the profile via §2. Ask if information is insufficient.
2. Only create folders actually used.
3. Keep bound methods thin; all setup logic in `main.go`, all business logic in `internal/domain`.
4. Create the shared error type (`internal/apperror` or similar) from profile B onward, even minimal.
5. Review the binding surface explicitly — don't bind a struct "for convenience" that exposes more than the app needs.
6. Leave `frontend/` where `wails init` puts it (§ W6) — no reason to move it.
7. Don't create a multi-app or multi-module layout without an identified second consumer.
8. Generate nothing tied to a forge or CI system.
9. Document W1–W6 in the project README.
10. **Route final build artifacts to `out/`** at the repository root — `out/release/` and `out/debug/`, gitignored.

    For a plain Go binary (the CLI), `go build` writes directly there:

    ```bash
    # release
    go build -o out/release/<name> ./cmd/<name>
    # debug — disables optimizations/inlining for a better debugger experience
    go build -gcflags="all=-N -l" -o out/debug/<name> ./cmd/<name>
    ```

    For the Wails app itself, `wails build` targets production by default (it applies `-ldflags "-w -s"` and production build tags internally) and doesn't cleanly separate into a release/debug pair the way a plain `go build` does. For the release artifact, set `"build:dir"` in `wails.json` (defaults to `build`) to point at `out/release`, or copy `build/bin/` there as a post-build step — verify the exact mechanism against the Wails CLI version in use, since it has shifted between v2 and v3. For a debug artifact, Wails' own documentation supports building manually via `go build` directly (bypassing `wails build`) with the `-tags dev -gcflags "all=-N -l"` flags it uses internally for `wails dev`, redirected to `out/debug/`.

## 6. Anti-patterns — audit checklist

| # | Symptom | Diagnosis |
|---|---|---|
| 1 | A component imports from `bindings/` (`wailsjs/`) directly | No `ipc/` layer — see shared React reference §2 |
| 2 | `app.go` methods mirror `internal/domain` 1:1 | Layer with no added value |
| 3 | Business logic inside a bound method's body | `internal/domain` not testable without Wails |
| 4 | Bare `error` returned from a bound method | Frontend can't react precisely (W4) |
| 5 | A struct bound "for convenience" exposing unrelated methods | No manifest to catch this later — it's the permission surface, treat it as one |
| 6 | Many small Go packages under `internal/` with circular imports | Premature split |
| 7 | Blocking bound call > 1 s with no `EventsEmit` progress | Frozen UX, no cancellation (W5) |
| 8 | Shared state mutated from a goroutine without a mutex | Race condition |
| 9 | Business logic duplicated in React and Go | W2 boundary never settled |
| 10 | `internal/domain` importing `context` from Wails runtime | Coupled to Wails, can't be reused by `cmd/cli` or tested standalone |
| 11 | Multiple Go modules (`go.work`) with no independent-release justification | Unnecessary tooling complexity |
| 12 | Hand-written TS types duplicating what `wails generate module` already produces | Redundant, will drift |
| 13 | Missing or manual DB migrations | Non-reproducible schema |
| 14 | Frontend moved out of `frontend/` without reason | Fighting the tool's default for no benefit |
| 15 | No test exercising `internal/domain` without a running Wails app | Signals logic and Wails runtime were never actually separated |

## 7. Evolution path

Same caution as the Tauri skill: **no easy migration from B to C.** What changes is the shape of the boundary.

1. Start with **B**, `internal/domain` already free of Wails-runtime imports.
2. Keep logic in React while it's purely UI-related.
3. Put every authoritative business rule in `internal/domain`.
4. Move to a multi-app layout (`cmd/desktop`, `cmd/cli`) only once a `internal/domain` module has a stable boundary **and** a second consumer exists.
5. Keep it a single Go module unless independent versioning is a real need (§3.C).

## 8. Prompts (standalone use)

**New project, profile to determine**
```
Project: <2-3 sentence description>
Expected system access: <files / git / processes / DB / none>
Team: <size, Go experience or not>
Planned other consumer of the business logic: <yes/no, which>

Step 1: recommend a profile (A/B/C) with justification, and propose values
for W1–W6. Create no files.
Step 2: after approval, scaffold following §5, and read react-conventions.md
for the frontend side.
```

**Full audit**
```
Audit this project:
1. Identify the actual profile and the gap with the appropriate one.
2. Walk the §6 checklist point by point, with files and lines as evidence.
3. Specifically review every Bind() call as a permission-surface question —
   is each exposed method something the app actually needs client-accessible?
4. Assess W1–W6 as currently implemented.
5. Rank issues by increasing cost to fix.
Modify no files.
```

**Binding surface review**
```
List every struct and method exposed via Bind() in this project. For each,
state what it allows the frontend to do, and whether that's the minimum
necessary surface. Flag anything bound "for convenience" that exposes more
than the current UI actually calls.
```

**Moving from B to C**
```
Assess extracting internal/domain into a shape usable by a second consumer
(cmd/cli or cmd/server) per §7. Check the prerequisite: is internal/domain
free of Wails-runtime imports? If not, list what to break first. If yes,
propose the cmd/ layout and justify keeping a single Go module vs go.work.
```

## 9. Evolving toward a server with remote clients

Same three points as the Tauri skill's §9, restated for Go:

1. **Not everything in `internal/domain` can centralize.** Local file/process/Git access is inherently client-side. Classify module by module before extracting anything.
2. **Design W2 as if it were already a network API.** This is unusually cheap in Go: a bound method and an HTTP handler can both call the same `internal/domain` function directly, so the "reuse the boundary shape later" argument from the Tauri skill is even more literal here — the same function signature often serves both, with only the transport wrapper (`Bind()` vs `http.HandlerFunc`) differing.
3. **Multi-user auth and data isolation remain a separate, unaddressed problem** — more so than in Tauri, since there's no capability system to even partially lean on. Authentication, sessions, and tenant isolation need their own design pass on the server side.
