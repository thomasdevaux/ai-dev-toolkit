# Reference — React Frontend Conventions (shared: Tauri & Wails)

React is the mandated frontend across both web-tech-based stacks (Tauri + Rust, Wails + Go). This file documents the conventions that stay identical regardless of which backend is behind it — the goal is that a developer moving from a Tauri project to a Wails project (or vice versa) finds the same frontend shape, and only the backend language changes.

This file is intentionally backend-agnostic. For the generated-bindings mechanism specific to each backend, see that skill's own reference file.

## 0. Escape hatch: plain HTML/JS for very small tools

Both Tauri and Wails will serve a folder of plain static files with no build step at all — an `index.html`, a `script.js`, a `style.css`. For a genuinely tiny tool (one screen, a few controls, no dynamic lists), this is meaningfully simpler than React: nothing to install, no build, no component model to learn, and direct DOM manipulation that reads much like ordinary imperative code.

**The threshold, stated plainly**: below roughly one screen with a few fields and a simple list, plain HTML/JS is simpler. Above that — several views, conditional rendering, lists that grow and shrink, state that must stay in sync across the interface — React becomes simpler to *maintain*, even though it costs more to start. Without a reactive framework, every state change has to be reflected onto every affected DOM element by hand, which degrades quickly.

If plain HTML/JS is chosen, keep §2's rule anyway: route all backend calls through a single `ipc.js` module rather than calling bindings from arbitrary places. Everything else below assumes React.

## 1. Folder shape (identical in both stacks)

```text
frontend-src/                     # actual path is src/ (Tauri, Wails default) — content below is what goes inside it
├── components/                   # presentation only, no calls to backend
├── features/                     # domain-oriented slices
│   └── <feature>/
│       ├── components/
│       ├── hooks/
│       └── index.ts
├── pages/
├── ipc/                          # THE ONLY place generated bindings are called
│   ├── client.ts                 # thin wrapper: calls generated bindings, maps errors, no business logic
│   └── <domain>.ts
├── bindings/                     # generated by the backend toolchain — never hand-edit
├── store/                        # global state, see §3
├── lib/                          # pure utilities
├── App.tsx
└── main.tsx
```

**Why `bindings/` and `ipc/` are two separate folders, not one**: `bindings/` is regenerated by the backend's tooling (`wails3 generate bindings`, or a Tauri type-generation plugin) and must never be edited by hand — a hand edit is silently overwritten on the next build. `ipc/` is hand-written, stable, and is where error mapping and any request shaping happens. Components never import from `bindings/` directly; they only ever import from `ipc/`.

## 2. The one rule that matters most

**No component calls a generated binding directly.** Whether that's `invoke('open_project')` (Tauri) or `OpenProject()` imported from `bindings/...` (Wails), it goes through `ipc/`, not a component. This is the single most common structural mistake in both stacks, and it's the same mistake either way: it couples UI code to the backend's calling convention, and it means error handling gets reinvented per component instead of centralized once in `ipc/client.ts`.

## 2b. Server state: TanStack Query over `ipc/`

`ipc/` returns promises. Left at that, every component that calls the backend
re-implements the same four things by hand: a loading flag, an error branch, a
way to refetch, and remembering to refresh whatever a mutation invalidated. It
is written slightly differently each time, and the fourth one is the one that
gets forgotten.

Use TanStack Query as the layer above `ipc/`:

- **Query keys mirror the `ipc/` split** — `['<domain>', …]`, one namespace per
  `ipc/<domain>.ts` file, so the cache is organized the way the backend surface
  already is.
- **Invalidation after mutation is the default** — a mutation invalidates the
  keys it affects rather than each component refetching on its own schedule.
- **§2's rule still wins.** Query wraps `ipc/`; it never calls a generated
  binding itself. `queryFn` and `mutationFn` call an `ipc/` function and nothing
  else — so the "only one place talks to the backend" property is preserved,
  with Query sitting above that boundary rather than punching through it.

`store/` (§3) keeps its role for genuine client state — selection, open panels,
draft form values. What comes from the backend belongs in Query's cache, not
mirrored into the store; keeping a second copy there is how the two drift.

## 3. State management

No hard mandate, but a default worth stating explicitly so it doesn't get re-litigated per project: a lightweight store (Zustand or Jotai) over Redux for apps of this size — internal tools and diagnostic utilities rarely need Redux's ceremony. If a project's state genuinely grows complex enough to want Redux-style patterns, that's a signal worth revisiting, not a reason to start there.

## 4. Error handling on the frontend

Two layers, not one:
- **React Error Boundaries** for rendering failures — a component throwing during render shouldn't take down the whole app.
- **Explicit typed handling at the `ipc/` boundary** for backend call failures — map the backend's typed error (Rust's serializable enum, or Wails' typed error result, see the backend-specific reference) to a user-facing message in `ipc/client.ts`, once, rather than scattering `try/catch` blocks per component with ad hoc messages.

## 5. TypeScript strictness

Strict mode on. No `any` at the `ipc/` boundary specifically — that's the one place where a loosely-typed call silently defeats the whole point of generating types from the backend. `any` elsewhere in the frontend is a normal code-review conversation; `any` in `ipc/` is a structural regression.

## 6. Testing

Vitest for components and `features/`. Mock the `ipc/` layer at its module boundary rather than mocking `bindings/` directly — this keeps tests stable across backend changes, since `ipc/`'s shape changes far less often than the generated bindings underneath it.

## 7. Styling

Left as a project decision — Tailwind, CSS modules, or plain CSS are all fine. The only shared rule: co-locate styles with the component they style, regardless of which approach is chosen, rather than a single global stylesheet that grows unbounded.

## 8. Anti-patterns (shared)

| # | Symptom | Diagnosis |
|---|---|---|
| 1 | A component imports from `bindings/` directly | Missing `ipc/` layer — see §2 |
| 2 | Hand edits inside `bindings/` | Will be silently lost on next generation |
| 3 | `try/catch` around backend calls repeated per component with different messages | Error mapping not centralized in `ipc/client.ts` |
| 4 | `any` used at an `ipc/` call site | Defeats the point of generated typing |
| 5 | Redux introduced for an app with a handful of screens | Ceremony without a corresponding need — reconsider a lighter store |
| 6 | Hand-rolled loading/error/refetch state around an `ipc/` call in a component | Re-implements what the server-state layer already does, differently each time — and post-mutation invalidation is what gets forgotten (§2b) |
| 7 | Backend data copied from the query cache into `store/` | Two sources of truth for the same data; they drift (§2b) |
